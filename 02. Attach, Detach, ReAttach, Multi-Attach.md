## 1. EBS Topics to Cover

Below is a structured list of all topics you should cover when teaching EBS for AWS certification and real-world usage:

### 🔵 Core Concepts
- What is Amazon EBS? (Block storage vs Object storage vs File storage)
- EBS vs Instance Store (Ephemeral vs Persistent)
- EBS Availability Zone binding (EBS is AZ-specific)
- EBS Volume Lifecycle (Create → Attach → Use → Detach → Delete)

### 🔵 Volume Types
- **gp2 vs gp3** – General Purpose SSD (differences, burst credits, throughput)
- **io1 vs io2** – Provisioned IOPS SSD (high-performance, Multi-Attach support)
- **st1** – Throughput Optimized HDD (big data, log processing)
- **sc1** – Cold HDD (infrequent access, lowest cost)
- **Magnetic (standard)** – Legacy, rarely used

### 🔵 Key Features & Labs
- Attach a new EBS volume to an EC2 instance (console + MobaXterm)
- Format, mount, and write data to EBS
- Detach EBS from one instance and reattach to another (data persistence proof)
- EBS Multi-Attach (io1/io2 – multiple EC2s in same AZ)
- EBS Snapshots (manual + automated using Data Lifecycle Manager)
- Creating AMI from EBS-backed instance
- EBS Encryption (at-rest, in-transit, KMS integration)
- Encrypting an unencrypted volume via Snapshot copy
- EBS Elastic Volumes (resize, change type, adjust IOPS without downtime)
- EBS Optimized Instances
- EBS Performance (IOPS, throughput, burst behavior)
- EBS Fast Snapshot Restore (FSR)
- EBS vs EFS – When to use which
- Cross-Region Snapshot copy
- Recycle Bin for EBS Snapshots (accidental deletion protection)
- EBS CloudWatch Metrics (VolumeReadOps, VolumeWriteOps, BurstBalance, etc.)

## 2. EBS Fundamentals – Quick Reference

| Feature | Detail |
|---|---|
| Storage Type | Block Storage |
| Scope | Single AZ (cannot attach across AZs) |
| Attachment | One instance at a time (except io1/io2 with Multi-Attach) |
| Persistence | Data persists after instance stop/restart |
| Root Volume | Deleted on termination by default (configurable) |
| Data Volume | NOT deleted on termination by default |
| Encryption | AES-256, powered by AWS KMS |
| Snapshot storage | Stored in Amazon S3 (managed by AWS, not visible to you) |

## 3. LAB 1 – Attach EBS, Write Data, Detach & Re-attach to New VM (Lab 1 Demonstrated in Batch 10)

### 🎯 Goal
- Launch **VM-1**, attach a new EBS volume, write data to it
- Detach EBS from VM-1
- Attach it to **VM-2** and verify the data is still there

### 🗺️ Architecture
```
Mumbai Region (ap-south-1)
└── AZ: ap-south-1a
    ├── VM-1 (Amazon Linux 2023)
    │   └── /dev/xvdf → EBS Volume (10 GB gp3)  ← Write data here
    │
    ├── EBS Volume detached from VM-1
    │
    └── VM-2 (Amazon Linux 2023)
        └── /dev/xvdf → Same EBS Volume  ← Verify data here
```

> ⚠️ **CRITICAL**: Both VM-1 and VM-2 must be in the **same AZ** (ap-south-1a). EBS is AZ-bound.

---

### STEP 1 – Launch VM-1

1. Open AWS Console → **EC2** → **Instances** → Click **Launch Instances**

2. Fill in the following:
   - **Name**: `EBS-Lab-VM1`
   - **AMI**: `Amazon Linux 2023 AMI` (select the latest 64-bit x86)
   - **Instance Type**: `t2.micro` (Free Tier eligible)
   - **Key Pair**: Select an existing key pair OR create a new one (e.g., `kastro-mumbai-key`)
     - If creating new: Download the `.pem` file immediately and save it

3. **Network Settings**:
   - VPC: Default VPC
   - Subnet: Choose **ap-south-1a** subnet (this is critical — note the AZ)
   - Auto-assign Public IP: **Enable**
   - Security Group: Create a new one
     - Name: `EBS-Lab-SG`
     - Inbound Rule: SSH | Port 22 | Source: My IP

4. **Configure Storage** (Root Volume):
   - Leave the default 8 GB gp3 root volume as-is
   - Do NOT add extra volumes here — we'll do that separately

5. Click **Launch Instance** → Wait for the instance to reach **Running** state

---

### STEP 2 – Create a New EBS Volume

1. In EC2 Console, go to **Elastic Block Store** → **Volumes** → Click **Create Volume**

2. Fill in:
   - **Volume Type**: `gp3`
   - **Size**: `10 GiB`
   - **IOPS**: `3000` (default for gp3)
   - **Throughput**: `125 MiB/s` (default)
   - **Availability Zone**: **ap-south-1a** ← Must match VM-1's AZ
   - **Snapshot ID**: Leave blank (No snapshot)
   - **Encryption**: Unchecked for now (or enable if you want to practice encryption)
   - **Tags**: Key = `Name`, Value = `EBS-Data-Volume`

3. Click **Create Volume**

4. Wait for the volume Status to change from `creating` → **`available`**

---

### STEP 3 – Attach EBS Volume to VM-1

1. In **Volumes** list, select your `EBS-Data-Volume`
2. Click **Actions** → **Attach Volume**
3. In the dialog:
   - **Instance**: Start typing `EBS-Lab-VM1` and select it
   - **Device name**: `/dev/sdf` (AWS maps this to `/dev/xvdf` inside Linux)
4. Click **Attach Volume**
5. Wait for the volume State to show **`in-use`**

---

### STEP 4 – Connect to VM-1 via MobaXterm

1. Open **MobaXterm**
2. Click **Session** → **SSH**
3. Fill in:
   - **Remote Host**: (Copy Public IPv4 DNS from EC2 console)
   - **Username**: `ec2-user`
   - **Advanced SSH Settings** → Check **Use private key** → Browse to your `.pem` file
4. Click **OK** to connect

---

### STEP 5 – Format, Mount, and Write Data on VM-1

Once connected via MobaXterm, run the following commands one by one:

#### 5.1 – List available disks (confirm EBS is attached)
```bash
lsblk
```
**Expected output** – you should see `xvdf` (10G) without a mount point:
```
NAME     MAJ:MIN RM SIZE RO TYPE MOUNTPOINTS
xvda     202:0    0   8G  0 disk
└─xvda1  202:1    0   8G  0 part /
xvdf     202:80   0  10G  0 disk
```

#### 5.2 – Check if the disk has a filesystem
```bash
sudo file -s /dev/xvdf
```
Expected output: `/dev/xvdf: data`
> If it says `data`, it means the disk is raw (no filesystem) — this is expected for a brand-new volume.

#### 5.3 – Create an ext4 filesystem
```bash
sudo mkfs -t ext4 /dev/xvdf
```

#### 5.4 – Create a mount point directory
```bash
sudo mkdir /mnt/ebs-data
```

#### 5.5 – Mount the EBS volume
```bash
sudo mount /dev/xvdf /mnt/ebs-data
```

#### 5.6 – Verify the mount
```bash
df -h
```
You should see `/dev/xvdf` mounted at `/mnt/ebs-data` with ~9.8G size.

#### 5.7 – Write test data to the EBS volume
```bash
# Create a directory inside the EBS volume
sudo mkdir /mnt/ebs-data/kastro-test

# Write test files
sudo bash -c 'echo "Hello from Learn With KASTRO - EBS Lab Day 1" > /mnt/ebs-data/kastro-test/hello.txt'

sudo bash -c 'echo "This file was written on VM-1 in Mumbai Region ap-south-1a" > /mnt/ebs-data/kastro-test/server-info.txt'

# Write a larger dummy file (1MB) to simulate real data
sudo dd if=/dev/urandom of=/mnt/ebs-data/kastro-test/dummy-data.bin bs=1M count=1
```

#### 5.8 – Verify the data was written
```bash
ls -lh /mnt/ebs-data/kastro-test/
cat /mnt/ebs-data/kastro-test/hello.txt
cat /mnt/ebs-data/kastro-test/server-info.txt
```

#### 5.9 – Unmount the volume before detaching (VERY IMPORTANT)
```bash
# First unmount the volume
sudo umount /mnt/ebs-data

# Verify it's unmounted
df -h
# /dev/xvdf should no longer appear
```

> ⚠️ **ALWAYS unmount before detaching from AWS Console** — detaching without unmounting can cause filesystem corruption.

---

### STEP 6 – Detach EBS Volume from VM-1 (Console)

1. Go to EC2 Console → **Elastic Block Store** → **Volumes**
2. Select `EBS-Data-Volume`
3. Confirm its State is **`in-use`**
4. Click **Actions** → **Detach Volume**
5. In the confirmation dialog, click **Detach**
6. Wait for State to change back to **`available`**

---

### STEP 7 – Launch VM-2 (Same AZ as VM-1)

1. Go to EC2 → **Launch Instances**
2. Fill in:
   - **Name**: `EBS-Lab-VM2`
   - **AMI**: `Amazon Linux 2023 AMI`
   - **Instance Type**: `t2.micro`
   - **Key Pair**: Same key pair as VM-1 (`kastro-mumbai-key`)
   - **Subnet**: **ap-south-1a** ← Same AZ as the EBS volume
   - **Auto-assign Public IP**: Enable
   - **Security Group**: Select existing `EBS-Lab-SG`
3. Click **Launch Instance**

---

### STEP 8 – Attach EBS Volume to VM-2 (Console)

1. Go to **Volumes** → Select `EBS-Data-Volume` (State: available)
2. Click **Actions** → **Attach Volume**
3. Select **`EBS-Lab-VM2`** as the instance
4. Device name: `/dev/sdf`
5. Click **Attach Volume** → Wait for State: **`in-use`**

---

### STEP 9 – Connect to VM-2 via MobaXterm & Verify Data

1. Open a new MobaXterm session and SSH into VM-2 (use its Public IP)

#### 9.1 – Confirm the volume is attached
```bash
lsblk
```
You should see `xvdf` (10G) without a mount point — same volume, no filesystem format needed.

#### 9.2 – Mount the volume (no formatting needed — data already exists)
```bash
sudo mkdir /mnt/ebs-data
sudo mount /dev/xvdf /mnt/ebs-data
```

#### 9.3 – Verify all data from VM-1 is intact
```bash
ls -lh /mnt/ebs-data/kastro-test/
cat /mnt/ebs-data/kastro-test/hello.txt
cat /mnt/ebs-data/kastro-test/server-info.txt
ls -lh /mnt/ebs-data/kastro-test/dummy-data.bin
```

**Expected Output:**
```
Hello from Learn With KASTRO - EBS Lab Day 1
This file was written on VM-1 in Mumbai Region ap-south-1a
```

✅ **Data is fully preserved!** This proves EBS is persistent block storage — the data lives on the volume, not on the instance.

---

### STEP 10 – Cleanup (After Lab)

```bash
# On VM-2 — unmount before cleanup
sudo umount /mnt/ebs-data
```

Then in AWS Console:
1. Detach the volume from VM-2
2. Terminate both instances (VM-1 and VM-2)
3. Delete the `EBS-Data-Volume` (Action → Delete Volume)

## 4. LAB 2 – EBS Multi-Attach (io1/io2 Provisioned IOPS) (Lab 2 Shown the Option in Batch 10)

### 🎯 What is EBS Multi-Attach?

EBS Multi-Attach allows a **single io1 or io2 EBS volume** to be simultaneously attached to **up to 16 EC2 instances within the same AZ**. This is useful for clustered databases, high-availability applications, and shared storage scenarios — where multiple instances need concurrent read/write access to the same block device.

### ⚠️ Important Constraints
| Constraint | Detail |
|---|---|
| Volume Types | io1 or io2 ONLY (gp2, gp3, st1, sc1 do NOT support Multi-Attach) |
| AZ Scope | All instances must be in the **same AZ** |
| Max Instances | 16 EC2 instances simultaneously |
| Filesystem | Must use a **cluster-aware filesystem** (e.g., GFS2, OCFS2) |
| Standard ext4/xfs | ❌ Not safe for concurrent writes — risk of corruption |
| OS | Must be Linux (Windows not supported for Multi-Attach) |

> 📌 **For this lab**, we will demonstrate the attach/mount process with read-only mounts on the second instance to keep it safe without a cluster filesystem.

---

### 🗺️ Architecture

```
Mumbai Region (ap-south-1)
└── AZ: ap-south-1a
    ├── MA-VM1 (Amazon Linux 2023)  ──┐
    │                                  ├── Both attached to same io2 volume
    └── MA-VM2 (Amazon Linux 2023)  ──┘
              ↓
    io2 EBS Volume (Multi-Attach enabled)
    /dev/xvdf on both instances simultaneously
```

---

### STEP 1 – Launch MA-VM1

1. EC2 → **Launch Instances**
2. Fill in:
   - **Name**: `MA-VM1`
   - **AMI**: Amazon Linux 2023
   - **Instance Type**: `t3.micro` (t3 supports EBS-optimized by default)
   - **Key Pair**: `kastro-mumbai-key`
   - **Subnet**: `ap-south-1a`
   - **Auto-assign Public IP**: Enable
   - **Security Group**: `EBS-Lab-SG` (SSH port 22)
   - **Storage**: Leave root volume default (8 GiB gp3)
3. Click **Launch Instance**

---

### STEP 2 – Launch MA-VM2

1. EC2 → **Launch Instances**
2. Fill in (same as MA-VM1 except name):
   - **Name**: `MA-VM2`
   - **AMI**: Amazon Linux 2023
   - **Instance Type**: `t3.micro`
   - **Key Pair**: `kastro-mumbai-key`
   - **Subnet**: `ap-south-1a` ← Must be same AZ
   - **Auto-assign Public IP**: Enable
   - **Security Group**: `EBS-Lab-SG`
3. Click **Launch Instance**

---

### STEP 3 – Create an io2 EBS Volume with Multi-Attach Enabled

1. EC2 → **Elastic Block Store** → **Volumes** → **Create Volume**

2. Fill in:
   - **Volume Type**: `io2` (Provisioned IOPS SSD)
   - **Size**: `10 GiB`
   - **IOPS**: `100` (minimum is 100 for io2; billed per IOPS provisioned)
   - **Availability Zone**: `ap-south-1a` ← Must match both VMs
   - **Encryption**: Optional — leave unchecked for now
   - **Multi-Attach**: ✅ **Check "Enable Multi-Attach"**
     > This option only appears when Volume Type is io1 or io2
   - **Tags**: Key = `Name`, Value = `EBS-MultiAttach-Volume`

3. Click **Create Volume**
4. Wait for State: **`available`**

---

### STEP 4 – Attach the io2 Volume to MA-VM1

1. Select `EBS-MultiAttach-Volume`
2. **Actions** → **Attach Volume**
3. Instance: `MA-VM1`
4. Device Name: `/dev/sdf`
5. Click **Attach Volume** → State: `in-use`

---

### STEP 5 – Attach the SAME io2 Volume to MA-VM2

1. Select the **same** `EBS-MultiAttach-Volume` (State: in-use)
2. **Actions** → **Attach Volume**
3. Instance: `MA-VM2`
4. Device Name: `/dev/sdf`
5. Click **Attach Volume**

> ✅ Notice: AWS allows you to attach the same volume to a second instance without detaching from the first — this is the Multi-Attach feature in action.

6. Both MA-VM1 and MA-VM2 are now using the same EBS volume simultaneously.

---

### STEP 6 – Connect to MA-VM1 & Write Data

Open MobaXterm → SSH into MA-VM1:

#### 6.1 – Verify volume is visible
```bash
lsblk
# xvdf should appear with 10G
```

#### 6.2 – Create filesystem on the volume (do this on MA-VM1 ONLY)
```bash
sudo mkfs -t ext4 /dev/xvdf
```

> ⚠️ Only format from ONE instance. If you format from MA-VM2 after writing data from MA-VM1, you will erase everything.

#### 6.3 – Mount on MA-VM1 (read-write)
```bash
sudo mkdir /mnt/shared
sudo mount /dev/xvdf /mnt/shared
df -h
```

#### 6.4 – Write data from MA-VM1
```bash
sudo bash -c 'echo "Written from MA-VM1 at $(date)" > /mnt/shared/from-vm1.txt'
sudo bash -c 'echo "Multi-Attach Lab - Learn With KASTRO" >> /mnt/shared/from-vm1.txt'
cat /mnt/shared/from-vm1.txt
```

---

### STEP 7 – Connect to MA-VM2 & Read Data (Read-Only Mount)

Open a new MobaXterm session → SSH into MA-VM2:

#### 7.1 – Verify volume is visible
```bash
lsblk
# xvdf should appear on MA-VM2 too (same volume)
```

#### 7.2 – Mount as READ-ONLY on MA-VM2
```bash
sudo mkdir /mnt/shared
sudo mount -o ro /dev/xvdf /mnt/shared
# -o ro = read-only option (safe without cluster filesystem)
```

#### 7.3 – Read the data written by MA-VM1
```bash
ls -lh /mnt/shared/
cat /mnt/shared/from-vm1.txt
```

**Expected Output:**
```
Written from MA-VM1 at Tue Jun 16 10:30:00 UTC 2026
Multi-Attach Lab - Learn With KASTRO
```

✅ **Data written on MA-VM1 is readable on MA-VM2 from the same EBS volume simultaneously!**

---

### STEP 8 – Write from MA-VM2 (Advanced – Understand the Risk)

> This step shows the risk of concurrent writes without a cluster filesystem.

```bash
# On MA-VM2 — remount as read-write (for demo only)
sudo umount /mnt/shared
sudo mount /dev/xvdf /mnt/shared

# Write from MA-VM2
sudo bash -c 'echo "Written from MA-VM2 at $(date)" > /mnt/shared/from-vm2.txt'
```

> ⚠️ **Warning**: Writing from both instances simultaneously to the same non-cluster filesystem (ext4) can cause filesystem corruption in production. In real Multi-Attach scenarios, use **GFS2** or **OCFS2** which manage concurrent writes safely with distributed locks.

---

### STEP 9 – Detach Multi-Attach Volume

You must detach from each instance separately:

1. **Unmount on MA-VM1**:
   ```bash
   sudo umount /mnt/shared
   ```
2. **Unmount on MA-VM2**:
   ```bash
   sudo umount /mnt/shared
   ```

3. In AWS Console → **Volumes** → Select `EBS-MultiAttach-Volume`
4. **Actions** → **Detach Volume** → Select **MA-VM1** → Detach
5. Repeat → **Actions** → **Detach Volume** → Select **MA-VM2** → Detach
6. State returns to **`available`**

---

### STEP 10 – Multi-Attach Cleanup

1. Terminate MA-VM1 and MA-VM2 from EC2 console
2. Delete the `EBS-MultiAttach-Volume`

## 5. EBS Volume Types – Comparison Table

| Type | Category | Use Case | Max IOPS | Max Throughput | Multi-Attach |
|---|---|---|---|---|---|
| **gp3** | SSD | General purpose, boot volumes, web apps | 16,000 | 1,000 MiB/s | ❌ |
| **gp2** | SSD | Legacy general purpose (use gp3 instead) | 16,000 | 250 MiB/s | ❌ |
| **io2** | SSD | Databases, mission-critical, high IOPS | 256,000 | 4,000 MiB/s | ✅ |
| **io1** | SSD | High-performance, legacy | 64,000 | 1,000 MiB/s | ✅ |
| **st1** | HDD | Big data, log processing, sequential reads | 500 | 500 MiB/s | ❌ |
| **sc1** | HDD | Cold data, infrequent access, archival | 250 | 250 MiB/s | ❌ |

> 💡 **Tip**: For new deployments, always prefer **gp3** over gp2 (better baseline performance, cheaper). Use **io2** for databases requiring high IOPS or Multi-Attach.

## 6. Best Practices & Common Pitfalls

### ✅ Best Practices
- Always **unmount** the EBS volume before detaching from AWS Console
- Use **gp3** for most workloads (better perf/cost than gp2)
- Enable **EBS encryption** for sensitive data (no performance penalty)
- Take **regular snapshots** using Data Lifecycle Manager (DLM)
- Enable **Delete on Termination: No** for data volumes (do not auto-delete)
- For Multi-Attach, always use a **cluster-aware filesystem** in production
- Use **EBS Elastic Volumes** to resize or change type without downtime

### ❌ Common Pitfalls
- Detaching without unmounting → **filesystem corruption**
- Trying to attach EBS across AZs → **Not possible** (use snapshot + create in target AZ)
- Using Multi-Attach with ext4 for concurrent writes → **Data corruption risk**
- Forgetting that gp2 IOPS are burst-credit based → **Throttling under sustained load**
- Deleting a snapshot that is the base of an AMI → **AMI becomes unusable**
- Not enabling encryption at volume creation → **Cannot encrypt an existing volume directly** (must snapshot → copy encrypted → restore)
